## 保存データ・共有範囲・失敗時の扱い

| 種類 | 実装で守ること | 確認方法 |
| --- | --- | --- |
| 昔の作品と控え | 新しい目標、台本の行種、期待する結末、素材の確認状態などは、従来のデータで値が欠けていても開けるようにする。新しい形式が必須なら、保存形式の版と必要機能を明記し、対応外の読み込みは書き込み前に止める。 | 未編集の控え・以前作った教材・作者が改変した教材を用意する。開く→編集→完全保存→別のコピーへ復元し、場面・台詞・分岐の参照、固定した世界、添付、過去の稿を照合する。[保存形式](../spec/FILE_FORMAT.md) |
| 一括操作・取消 | 一括置換、段落復元、翻訳表の取込、メモ変換、並べ替えは「対象・元の版を確認→差を表示→一度に保存」とする。確定直前に他の変更があれば再比較する。二重押し・容量不足・中断では全体が元の状態か、一度だけ確定した状態になるようにする。 | 同じ操作の二重実行、別タブでの先行編集、書き込み中断、取消と再試行を行い、変わるはずの本文・注釈・参照と、影響外の場面をそれぞれ照合する。 |
| 手元の作業位置 | 下書き・カーソル・検索条件・試読・練習を別々に扱う。利用者、作品、必要な版を付けて保存し、以前の段落が消えた場合は理由と移動先を示す。 | 執筆と試読で違う章を開いて順に再開する。他作品・別利用者・閲覧権限の失効後にも同じ手順を試す。 |
| 読者に渡すもの | 同じ受取人・版・公開設定から、本文・候補・件数・ファイルを一貫して作る。作者の除外理由は作者側で見る。自由記述の本文や素材の中身は出力前に作者が通読・試聴できるようにする。 | 秘密の試験語と非公開の添付を入れ、作者と読者を分けて、検索・候補・リンク先・ファイル内部を確認する。権限のない項目は名前・件数・所在も出さない。 |
| 長い作品の応答 | 章・検索結果・稿の比較・読者用の全文は、必要なまとまりごとに開けるようにする。検索や比較の途中で中断しても、それまでの入力や確定済みの保存を失わないようにする。 | 既存の標準・大型の試験作品で、初回表示、文字入力、絞り込み、二版比較の前後を同じ条件で測る。対象版・件数・時間・メモリを以前の性能計画と照合する。[性能と確認の進捗](codex-next-stages-2026-10-19/STATUS.md) |

### 各工程の試験と引き渡し

1. 変更前に上の該当手順を一度実行し、対象の版、使った試験用作品、操作と結果を記録する。既存の試験で届かない分岐を先に特定する。
2. 工程表の既存試験に正常・失敗・取消の必要な組み合わせを追加する。手元の確認は変更点に絞り、同じ試験を繰り返す代わりに別の失敗条件を確認する。文書の確認には `npm run check:docs` と `npm run check:completion-plan` を使う。
3. 実装を含む変更は既存の自動検査に載せる。単体試験の基準は `npm test -- --maxWorkers=1 --fileParallelism=false`、製品ビルドは `npm run build`。画面を通す試験は `npm run test:e2e -- tests/e2e/manuals-sample.spec.ts` のように対象を指定して再現できる。正式判定はリポジトリの[自動検査](../../.github/workflows/ci.yml)と[従来の受入計画](../plan/COMPLETION_ACCEPTANCE.md)に従う。
4. 各実装PRに、案番号、対象の版、変更前後の結果、旧データ・異常系の結果、実機または別アカウントで残る確認を記す。新しい画面操作は[アプリ内の説明](../../src/manuals/content.ts)にも反映する。実機や専用共有環境が揃わない場合は、その確認だけ「未確認」とし、独立した工程を進める。
5. 問題が出たら一括操作は取消または操作前の復元点で、製品変更は該当する小さな変更単位で戻す。新しい形式で保存済みの作品は旧版で上書きせず、読める版で控えを確保して復旧手順を試す。案ごとの合格には、自動検査の結果と、その案で指定した実機・権限・復元の結果をそろえる。
