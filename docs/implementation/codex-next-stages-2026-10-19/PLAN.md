## 1. この計画で変更すること

前回レビューのNP01〜16をすべて残し、実行順を以下へ更新する。元要件・検査の縮小は行わない。以前の「受入を一式完了 → 性能改善 → もう一度最終受入」という依存を、**基準と検証の準備 → 比較して改善 → 最終候補で正式受入**に組み替える。

原PR #59の [共通条件8と第3段階作業5](../codex-three-phase-2026-10-17/PLAN_ALL_STAGES.md) は、各製品PRの必須全件・3ブラウザー検査と、統合した最終候補での重い正式試験を区別している。この計画もその条件に従う。第1段階の終了は「正式受入の完了」ではない。

| 分割するNP | 準備・途中で行うこと | 最終候補で行うこと |
| --- | --- | --- |
| NP05 | 1Aで変更前測定、1Dで比較設計。2A〜3Aの個別比較にも基準を使用 | 3Bで最終の速度・仕事量・保持量を同条件比較 |
| NP06 | 1Dで入力・手順・独立期待・出力先・終了確認・再開方法を準備 | 3Bで正式30/180/実7200/full113・同全量異常系を実行 |
| NP07 | 1Dで原104/116/464/24/6/68と現在の不足の暫定対応表を作成 | 3Cで実結果を逐条判定し、証拠束の再取得・独立照合まで確定 |
| NP08 | 1Cで原22外部条件と別3残条件の準備を完了 | 3Cで必要な実条件・担当・実施状況を更新。実受入とは別 |
| NP16 | 個別PRの採用／不採用と局所結果を各引継ぎへ保存 | 3BのNP06と同じ実行を統合後受入として参照。3Cで対応を確定 |

NP05・NP06・NP07は準備部分だけで元NP全体を完了にしない。最終正式一式の重複はまとめるが、変更前の原30/180の原本が不足する場合や修正後の再試験は別途必要である。全期間の実行回数が一度と保証するものではない。

## 5. 並行開発の運用

| 場面 | 並行できる作業 | 直列にする接点 |
| --- | --- | --- |
| 1B内 | N05捕捉driverとRG verifierを別ファイルで作成 | run_supplements.py、共有test／manifestは統合担当が編集 |
| 1Bと1C | scripts/acceptance側と制作E2E／外部文書側 | 再現した製品不具合が同じpathへ広がった時は担当を再割当 |
| 2B内 | store／projectSummaryの保存担当とcatalog／derivedIndexes／一覧担当 | store.ts、共有型・失効APIに両方の変更が必要ならAPIを先に固定して順に統合 |
| 2A・2C | 実装と独立oracle／反例のレビュー | store.tsとApp.tsxの変更は常に1人。履歴→保存→部分読込→世界保持の順を守る |
| 3C | 逐条判定案と、原本を空領域へ取得する独立照合 | 判定確定と最上位manifestの更新は統合担当1人 |

通常は1依頼の統合担当1人＋必要時に最大2担当。1Bと1Cを同時に進める場合も、全体の統合担当を1人に決め、同時実装担当を合計2人までとする。全単位を同時に起動したり、子担当がさらに担当を増やしたりしない。承認待ちに独立作業を進めても、未統合コードをmainにあると仮定しない。

各担当は自分のpathと `handoffs/<ID>.md` だけを更新する。段階の集約時に1D・2C・3Cの担当が `STATUS.md` を更新する。マージ競合を自動解消しただけで統合検査を省略しない。

## 6. トークンと再調査を減らす仕組み

- 依頼文は対象IDを固定する。毎回の必読は短い共通条件・自分の依頼書・依存handoff。大きな原典は必要な節から参照する。
- 前回の判断・棄却理由・対象commit・実コマンド・証拠pathを残し、次の担当が同じ原因調査や既存機能の作り直しから始めないようにする。
- 子担当は狭い作業と必要資料だけで開始する。コード全文・会話全文・全生ログを各担当へ複製しない。通常出力は要約と証拠path、失敗時に必要箇所だけ開く。
- 同じstoreの文脈が必要な変更は2A、2Cの内部で順に扱う。保存と検索のように独立する処理は2Bで分担する。単に作業を細分化して同じ全文を毎回読む形を避ける。
- 途中で長くなる場合は完了した小区間をPRとhandoffへ固定し、同じ単位の残りから再開する。読んでいないログや実行中のプロセスを完了としない。
- 最終正式一式はNP06とNP16の共通証拠にする。ただし各製品PRの必須CI、比較に必要な基準測定、失敗後の再実行は維持する。

削減率の数値保証は置かない。可能なら利用環境が表示するinput/output token等の実績を記録し、表示されない場合は読み直した資料数・担当数・再開回数を記録する。推定値を実測tokenとして報告しない。#73で任意のローカル出力短縮ガイドが統合されたため、利用時はAGENTSとSkillに従う。RTK本体の有無を確認し、正式証拠や計測へ用途を広げない。

## 7. 最終候補と証拠を混ぜない

3Bは採用変更と検査器を統合したcleanな製品候補を封印する。実測中は同じsource／build／fixtureを維持する。3Cで証拠や説明を追加したcommitは、**検査した製品commitとは別に**記録する。証拠追加だけでHEADが変わっても、その新HEADを検査済み製品として付け替えない。必要に応じ製品候補の固定checkoutと証拠提出用checkoutを分け、既存sealのexact-head条件を維持する。

3Bには実7200秒の試験が含まれる。実行が中断した場合は、既存プロセス・receipt・終了記録を調べてから再開し、同じ試行へ二重実行や上書きをしない。実施可能な範囲を完了した最終PRでも、外部22件と別の残条件が未成立なら元releaseのBLOCKEDをそのまま報告する。
