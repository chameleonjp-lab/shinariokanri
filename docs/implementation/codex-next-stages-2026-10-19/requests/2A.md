# 2A：履歴要求の取消と本文取得の削減を順に比較・実装する

[全体計画](../PLAN.md)／[守る条件](../GUARDRAILS.md)／[依頼文](../PROMPTS.md)

**対応：** NP09 → NP10。この依頼書の指定範囲だけを進める。

**開始条件：** 1Dの設計と準備成果がmainへ統合済み。`handoffs/1D.md` と1Aで固定した比較基準への参照を確認する。

**目的：** 不要になった履歴読込を止め、その後にLarge／inlineへ本文取得の軽量化を広げる。

**構成：** historyPage / historyCommandの任意AbortSignalとUI世代を結合する。本文の軽量経路はmetadata全件の完全性を保持し、互換full readerを残す。

**技術・仕様：** 既存React / TypeScript / Dexie、Vitest、Playwright 3 engines、Python、GitHub Actionsの対象部分を使う。原仕様は共通条件G01〜G06と原PR #59を維持し、新しい依存追加は実測と必要性を判断する。

## NP09：古い履歴検索を取り消せるようにする

- [ ] **具体対応：** historyPage/historyCommandへ任意のAbortSignalを追加し、HistoryPanelから検索・ページ・作品切替時に取消す。表示世代とstoreのaccount/role/作品/版の所有を確認し、不要になった後続読込・復号を止める。
- [ ] **完了条件：** 最新要求だけが表示され、取消後の追加batch/復号が抑えられる。取消しない要求は元の全metadata検査を保持する。既に実行中のDB requestを止められない場合は、次の境界で止める範囲を明示する。
- [ ] 遅い旧query→速い新query、ページ往復、作品切替、権限撤回、詳細取得中の取消を検証する。旧結果が混ざらずdraft/選択が保たれ、取消しない時の元errorが隠れない。
- [ ] OFFの待ち時間とONの読込/復号回数を別々に比較し、追加負荷だけ増す案は不採用にする。

**対象path（既存は入口、新規案は実装時に作成）：**

- `src/ui/HistoryPanel.tsx`
- `src/storage/store.ts`
- `src/storage/historyMetadata.ts`
- `tests/optimization/history-cancellation.test.ts（新規案）`
- `tests/optimization/history-metadata.test.ts`

**戻し方：** 任意signalの追加とUI取消だけを戻す。永続DB・原履歴・形式契約は変えない。

## NP10：履歴本文の軽量化を広げる

- [ ] **具体対応：** 元Large/inline/過大metadataを含め、軽量metadata経路に入れない理由を実測する。まず全metadataの完全性を保って本文取得量を減らす。metadataのDB取得自体をページ量へ絞る案は、その後に別の完全性証明と採否比較を行う。
- [ ] **完了条件：** Standardの既存本文0を維持し、元Large・inline長履歴など現在本文を取得する対象で削減を実証する。ID・順序・検索・画面外欠損拒否、全writer、原子性、途中移行とrollbackは初段階から必須。O(page)には未取得metadataの完全性証明をさらに追加する。
- [ ] 単純なhistoryIds.sliceは原D04で棄却済み。画面外missing row、別作品/同ID、importOrigin、64復元点、旧inline、quota、中断、未知rowを全件対照で照合する。
- [ ] 通常save・import/clone・ACK・確定解決の全writerを初段階から照合する。DB内部表/移行を追加する案は版、原子更新、再構築、旧形式/未知形式の安全なfull reader fallback、移行前復元点を設計に含める。外部native1.0は維持する。

**対象path（既存は入口、新規案は実装時に作成）：**

- `src/storage/historyMetadata.ts`
- `src/storage/recordPartsDatabase.ts`
- `src/storage/store.ts`
- `tests/optimization/history-metadata.test.ts`
- `tests/optimization/history-page-oracle.ts`
- `tests/optimization/history-measurement.test.ts`

**戻し方：** 新表現を理解する互換full decoderを残して高速pathを停止する。旧binaryへ戻す場合は全本文検証後に旧envelopeへ原子的に書き戻す。DB downgradeや削除を戻し方にしない。

### 採用範囲の制限

- [ ] NP09は任意signalで呼出互換を保ち、実行中DB requestを物理的に止められない場合は次batch／復号境界の停止範囲を記録する。
- [ ] NP10の初段階はO(Nmetadata)を許容する。Standardで既存の本文0を壊さず、元Large／inline／過大metadataのうち現在本文を読む対象で効果を実証する。
- [ ] 通常save・import／clone・ACK・確定解決の全writer、quota／中断、移行前後、画面外欠損を初段階から検査する。O(page)を口実にこの検査を後回しにしない。
- [ ] metadata自体のO(page)取得は、未取得部分の完全性を証明する別の設計・比較が成立するまで保留する。単純なhistoryIds.sliceを採用しない。
- [ ] 内部表現を変更する案は互換full decoderによる戻し方まで一緒に実装・検証する。単なる旧reader復帰で新表現を読めなくしない。
