# 単位ごとの引継ぎテンプレート

各単位の担当者は、下の様式を `handoffs/<ID>.md` に記録する。中断や小分けPRでも同じファイルを現在の結論へ更新し、完了済のsubstepと次の一操作を残す。原本・詳細は各[依頼カードの一覧](README.md)から指定された保存先へ置き、引継ぎには所在とSHAを残す。

短い結論は**約40行を目安**にする。長い比較表・ログ・逐条表は詳細へリンクし、生ログ全体の転記は避ける。40行を超える場合も、証拠の識別・安全条件・未実行条件を省略しない。まだ存在しない原本や引継ぎはリンクを作らず、予定pathをコード表記にする。

## 記録する様式

以下の `<…>` を実測・実確認で置き換える。取得していない値は `未取得（理由）`、不要な値は `非該当（理由）` とし、推測で埋めない。

**自分自身を含む最終SHAを文書内へ自己参照させない。** 引継ぎ自身を含むevidence commitや最終PR headのSHAは、書き込むと再び変わるため、提出後のPR本文・CI記録で確定する。handoffには検証したproduct SHA、証拠path、PR URL、提出前に未確定である理由を残せる。既に確定した別の証拠commitや過去のCI headを記載する場合は、その対象と確認時点を明記する。

```markdown
# 引継ぎ: <ID> / <substep>
- 更新日時・担当: <UTC / 統合担当または所有path担当>
- 単位の状態: <未着手 / 進行中 / PR提出・統合待ち / 完了 / 比較済・不採用 / 阻害（理由あり）>
- 結論: <今回分かったこと、採否、次に進める範囲を2文以内>
- 対象NP・到達点: <各NPの状態 / baseline・準備・正式結果・確定を区別>

## 完了・残り・変更
- 完了したsubstep: <実装・準備・検証を区別し、具体的な到達点>
- 残りのsubstep: <同じ単位の未完了範囲と、後続単位へ渡す範囲>
- 未実行 / BLOCKED: <対象条件、理由、必要な環境・権限・入力、準備済の内容>
- 所有path・変更: <実際のpath、他担当と共有する境界、差分の目的>
- API・共有型・manifestの変更: <変更契約と利用側への影響、または変更なし>
- 採否と理由: <比較結果 / 採用・不採用・保留 / 保留を解く条件>

## 候補と証拠の識別
| 区分 | 実際の値・所在 |
| --- | --- |
| base | <開始時mainの完全commit SHA / branch / 確認日時> |
| product | <検証した製品commit SHA / tree SHA / 比較対象の同じ識別> |
| evidence | <確定済の証拠commit SHA・tree SHA / 記録対象product / 自己参照なら未確定理由と証拠path> |
| build | <生成元product / buildコマンド・条件 / build ID・成果物path・SHA> |
| fixture | <版・seed・件数・実素材bytes / 原本path・SHA> |
| 配信bytes | <実際に読み込ませた成果物・asset一覧のpath・SHA・bytes / buildとの対応> |
| 実行環境 | <OS・browser・runtime・測定条件 / baselineとの差> |
| PR | <URL / base・確認済head SHA / 自己参照する最終headは提出後に確定 / Draft状態 / 依存PR群> |
| merge確認 | <ユーザーの実merge有無 / merge commit / 確認日時 / 未統合ならその旨> |

## 検証と原本
- 実行: <正確なコマンド / exit code / 対象product・fixture / 結果・単位>
- CI: <run URL / run ID / attempt / head SHA / 結果 / 未実行・失敗・取消>
- 原本: <ログ・download・生値・reportの実在pathと各SHA / 関連する要件・条項>
- 有効範囲: <同一候補で成立する判定 / 候補変更で失効する証拠 / 必要な再取得>
- 詳細: <長い比較表・逐条表・追加run等の実在pathまたはURL>

## 次の一操作と戻し方
- 次の一操作: <実行可能な1操作 / 前提 / 未統合ならユーザーmerge待ちを明記>
- 戻し方: <対象PR・commitと戻す差分 / データへの影響・復元前提>
- 次の依頼: <ID・substep / 読む直前handoff / 所有path / 引継ぐ最小情報>

## 次に送るプロンプト
<PROMPTS.mdの該当文を基に、ID・substep・実PR・必要なhandoffを入れた、そのまま送れる依頼文>
```

## 判定・再開の規則

- **単位の状態とNP全体の状態を分ける。** 1Aや1Dの依頼範囲が終わっても、NP05・NP06・NP07は準備だけで完了にしない。外部条件も、準備済の項目と未実行・BLOCKEDの受入条件を別に記録する。
- `PR提出・統合待ち` はユーザーのmerge待ちを示す。CI成功でも未統合ならこの状態を使う。`完了` は指定単位の条件を満たし、必要な変更がユーザーにより統合された状態とする。依存作業の着手は実PRのmergeと必要なCI・証拠を再確認して決め、採否・阻害の判定は[GUARDRAILS.md](GUARDRAILS.md)と該当依頼カードに従う。
- 再開時は実PR・commit・tree・CI runとattemptを確認する。過去の履歴合格を、新しい製品候補や配信bytesへ付け替えない。証拠だけを追記してcommitが変わった場合も、productとevidenceを別に識別し、同じ製品・build・fixture・配信bytesである根拠を残す。
- 通常の担当は自分の `handoffs/<ID>.md` だけを更新する。全体の[STATUS.md](STATUS.md)は1D・2C・3Cの統合担当が更新する。STATUSの古い一覧を根拠に、直前の引継ぎやGitHubの状態確認を省かない。
- 次に送るプロンプトは[PROMPTS.md](PROMPTS.md)から必要な1本だけを選ぶ。同じ単位の残作業には再開文を使い、未着手の後続単位を一括で依頼しない。
