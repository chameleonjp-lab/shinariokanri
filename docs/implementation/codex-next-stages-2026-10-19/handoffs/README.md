# 実行結果の引継ぎ

**この計画PRの作成時点では、各単位の実施記録はまだない。** このフォルダーの存在や計画のmergeは、実装・検証・正式受入が完了した証拠にはならない。実際に作業した担当が記録するまで、`1A.md`〜`3C.md` は未作成とする。

## 1単位に1つの短い結論を残す

各単位の担当は[HANDOFF_TEMPLATE.md](../HANDOFF_TEMPLATE.md)を使い、`handoffs/<ID>.md` を作成・更新する。小分けPRや中断のたびに、unit・substep、完了範囲、残作業、原本の所在とSHA、実PR・CI結果、次の一操作、次に送るプロンプトを更新する。複数のPRに分けても、同じ単位の再開地点が1つの引継ぎから分かるようにする。

結論は約40行を目安にし、長いログ・比較表・逐条表は、各依頼カードが指定する原本・詳細へリンクする。行数を理由に候補識別・安全条件・未実行条件を削らない。存在しない証拠にリンクを作らず、未取得理由と予定pathをコード表記で残す。

状態は `未着手` / `進行中` / `PR提出・統合待ち` / `完了` / `比較済・不採用` / `阻害（理由あり）` を使う。CI成功でも未統合なら `PR提出・統合待ち` とし、`完了` は指定単位の条件を満たし、必要な変更がユーザーにより統合された状態とする。単位の依頼範囲とNP全体の到達点を併記し、NP05・NP06・NP07は準備だけで完了にしない。外部環境未提供は、準備済の内容と未実行・BLOCKEDの条件を分けて記録する。

## 読み順と着手条件

次回の担当は計画の[README.md](../README.md)、[GUARDRAILS.md](../GUARDRAILS.md)、[STATUS.md](../STATUS.md)、自分の依頼カード、カードが指定する直前の引継ぎを先に読む。同じ単位の再開では自分の引継ぎも読む。必要な原本だけをその所在から追加で確認し、不足する引継ぎを過去全履歴から推測しない。

引継ぎに書かれた実PR・base/head/product/evidence commit・tree・build・fixture・配信bytes・CI runとattemptを再確認する。依存PRはユーザーのmerge後に更新したmainから扱い、履歴合格を新候補へ付け替えない。未統合や必要な証拠不足があれば、その条件と実行可能な準備、次の一操作を明記する。

## 並行作業と全体一覧

通常の単位は自分の `handoffs/<ID>.md` を更新する。段階統合の1D・2C・3Cだけが、統合担当として全体の[STATUS.md](../STATUS.md)を更新する。並行する1B・1CがSTATUSを編集する運用にはしない。

STATUSは段階統合時の一覧スナップショットである。次の実行可否は、直前の引継ぎとGitHub上の実merge・CIも確認して判定する。実行依頼には[PROMPTS.md](../PROMPTS.md)の対象単位または再開文を1本だけ使う。
