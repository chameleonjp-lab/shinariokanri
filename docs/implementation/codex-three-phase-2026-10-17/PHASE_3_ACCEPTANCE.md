## 最重要：全段階共通の実施条件

1. 着手時にmain、open PR、HEAD/tree、対象の固定資料・検査入力・成果物を再取得。保護設定が未設定だったmainについても状態を確認し、設定変更は提案に留める。過去の資料にある「#48未統合」等の歴史記述を現在の状態と混同しない。既存機能・修正を重複実装しない。
2. 既存の104要件（B01–B24、F01–F60、N01–N20）、116受入ケースと464条項、24工程、6回帰群、68補助確認、形式の互換契約、元fixture/seed/実bytes/時間上限/取消・復元条件を削除・緩和・改名しない。追加X01–X12は未採用候補として別管理し、承認済み要件に自動昇格させない。
3. 既存の差分履歴・64操作ごとの復元点・編集用の履歴省略読込・差分書込・検証証拠の限定再利用・分割保存等は既存実装として再利用する。測定なしに「未実装」「遅い原因」と断定しない。
4. 守るべき不可侵条件：作品内IDの一意性、作者の入力・正式参照・履歴・固定版の不変性、真実／証言／仮説の違い、変更の一括確定、送信待ち・競合・拒否、旧形式の互換性、秘密／公開範囲／権限、完全ファイルからの全量復元、失敗時の元データ保全。速くなってもこれらが崩れた案は不採用。
5. 今回は実iPhone/iPad/PCによる実機試験は行わない。ブラウザ自動試験・ヘッドレス・自動のタッチ模擬は可能だが、実機合格と表現しない。22件の外部条件待ちは個別に実機依存と実認証・実サービス依存を分類し、後者は独立した許可済み試験環境・権限があれば検証、なければ保留。試験の代用で合格にしない。
6. 既存の別用途Supabase、本番DB、実ユーザー作品、認証・権限、支払、課金、公開・配備を変更しない。Codex Cloud environmentsを使用しない。秘密情報をPR・ログ・添付へ含めない。
7. 製品コードは新規ブランチから、影響範囲ごとにレビュー可能なDraft PRを作り、原因、変更ファイル、確認した原要件、前後の元測定値と生ログ、失敗・未実行、戻し方を記す。ユーザー以外はmergeせず、公開しない。CI失敗は原因を確認し、修正・再実行して最終状態を示す。承認待ちの間は別の独立作業を進められるが、同一pathを競合編集しない。
8. 速度・資源・正確性は別々に比較する。元数値は一切緩めず、原30回・180保存・600000ms・2000ms・7200秒の条件を変更しない。通常のPR検査は必要な影響範囲を先行し、各製品PRで必須全件・3ブラウザーの検査を通す。7200秒のような重い正式試験は統合された最終候補を同一条件で実施し、証拠の出所を固定する。


## 第3段階：制作機能の仕上げ・自動品質保証・引渡し

**目的**：元の要件全体が実際の制作作業としてつながり、実機以外で再現できる正常・失敗・例外を検証できるところまで完成させる。

### 作業

1. 104要件・116ケース・464条項、24工程、6回帰群を最新mainの製品コード、画面到達経路、使用fixture、実結果、欠落・外部条件に再対応付ける。実装が既にあれば修正や証拠の追加だけに限定する。
2. 小説／脚本、ゲーム制作者、世界設定監修、素材・翻訳、ディレクター／レビュー、個人のオフライン制作を想定し、「作成→入力→関連付け→本文→試読／検索／検査→変更履歴→公開範囲確認→出力→復元」を自動ブラウザーから連続して実行する。到達できない画面、不必要な入力、戻り位置の消失、未保存入力の喪失、意味の不明なエラー等、元要件に対する欠陥を修正する。実機でないタッチ模擬とキーボード・日本語文字列の検査は補助結果に限定する。
3. データの正確性を壊す例外を独立に試す：参照先不在、同名異ID、改名・分割・統合、異なる世界版、作者の真実／証言／仮説、状態の矛盾、分岐の到達不可、秘密出力、権限変更、重複送信、偽ACK、別アカウント、途中取消、未知major、破損bytes、途中保存／容量不足、復元後の再編集。
4. PRの検査時間を無駄なく短くする。対象差分ごとの早期検査とビルド／依存準備の重複抑制を検討するが、製品PRでは既存の必須試験数・assert・fixture・実ブラウザー3種・負のケース・失敗証拠を削らない。変更に関係のない純MarkdownだけのPRと製品／JSON／検査入力変更を区別し、証拠版が混ざらないようにする。並列化する場合は検査独立性と生証拠の完全性を実証する。
5. 原仕様の正式なStandard/Large各指標×30、原6条件×30の180保存、長時間7200秒、88,003記録＋113履歴・送信待ち＋実72MiB素材の完全ファイル、600000msの完全ファイル出力上限、2000ms進捗・取消を、変更後の同じ最終製品候補で再実行する。new/clone/cold・実bytesの照合と異常系も含める。重い試験は同じ資源上で直列に実施する。
6. X01～X12については、既存機能との重複・利用者価値・実装範囲・追加の受入ケース・互換/移行・費用・リスクを比較する採用判断資料を作る。**未採用のX機能を本体へ追加しない。** 個別採用が確定した場合だけ別PRに分けて実装し、その結果を元104要件の受入件数に混ぜない。
7. 元 `scripts/check_release.py` と24工程の判定を変更せず、原受入を根拠付きで更新する。実機試験、専用認証／サービス／対象ゲームに必要な実環境・権限が不足する部分は未実行・環境待ちのまま残し、自動試験結果で偽装しない。独立レビューに必要な再現物を揃える。

### 完了条件

- 正式な「自動・非実機で実行可能な」元受入条項を独立の実結果で判定し、元件数／元条件を維持。失敗・未実行・外部待ちを明確に区分し、差分のある原要件は修正されている。
- Standard/Large/長時間/障害/完全復元の生値、製品commit・build、fixture SHA、実ログ、検査結果、再実行コマンド、実証環境を保存する。速度とメモリの最終比較表を提供する。
- 製品CIと3ブラウザーの必須検査が成功し、証拠の保存・照合に成功する。元の公開判定が実機・実権限等でBLOCKEDならその結果を正しく保持し、合格・公開済みとはしない。
- 最終Draft PRに改善済み・要実機・要実認証・要対象ゲーム・要採用判断・その他の未解決を分け、再現方法と次に必要な一操作を残す。merge／公開はユーザーのみ。
