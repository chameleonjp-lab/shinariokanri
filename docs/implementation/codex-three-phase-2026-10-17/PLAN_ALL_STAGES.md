## 最重要：全段階共通の実施条件

1. 着手時にmain、open PR、HEAD/tree、対象の固定資料・検査入力・成果物を再取得。保護設定が未設定だったmainについても状態を確認し、設定変更は提案に留める。過去の資料にある「#48未統合」等の歴史記述を現在の状態と混同しない。既存機能・修正を重複実装しない。
2. 既存の104要件（B01–B24、F01–F60、N01–N20）、116受入ケースと464条項、24工程、6回帰群、68補助確認、形式の互換契約、元fixture/seed/実bytes/時間上限/取消・復元条件を削除・緩和・改名しない。追加X01–X12は未採用候補として別管理し、承認済み要件に自動昇格させない。
3. 既存の差分履歴・64操作ごとの復元点・編集用の履歴省略読込・差分書込・検証証拠の限定再利用・分割保存等は既存実装として再利用する。測定なしに「未実装」「遅い原因」と断定しない。
4. 守るべき不可侵条件：作品内IDの一意性、作者の入力・正式参照・履歴・固定版の不変性、真実／証言／仮説の違い、変更の一括確定、送信待ち・競合・拒否、旧形式の互換性、秘密／公開範囲／権限、完全ファイルからの全量復元、失敗時の元データ保全。速くなってもこれらが崩れた案は不採用。
5. 今回は実iPhone/iPad/PCによる実機試験は行わない。ブラウザ自動試験・ヘッドレス・自動のタッチ模擬は可能だが、実機合格と表現しない。22件の外部条件待ちは個別に実機依存と実認証・実サービス依存を分類し、後者は独立した許可済み試験環境・権限があれば検証、なければ保留。試験の代用で合格にしない。
6. 既存の別用途Supabase、本番DB、実ユーザー作品、認証・権限、支払、課金、公開・配備を変更しない。Codex Cloud environmentsを使用しない。秘密情報をPR・ログ・添付へ含めない。
7. 製品コードは新規ブランチから、影響範囲ごとにレビュー可能なDraft PRを作り、原因、変更ファイル、確認した原要件、前後の元測定値と生ログ、失敗・未実行、戻し方を記す。ユーザー以外はmergeせず、公開しない。CI失敗は原因を確認し、修正・再実行して最終状態を示す。承認待ちの間は別の独立作業を進められるが、同一pathを競合編集しない。
8. 速度・資源・正確性は別々に比較する。元数値は一切緩めず、原30回・180保存・600000ms・2000ms・7200秒の条件を変更しない。通常のPR検査は必要な影響範囲を先行し、各製品PRで必須全件・3ブラウザーの検査を通す。7200秒のような重い正式試験は統合された最終候補を同一条件で実施し、証拠の出所を固定する。

## 第1段階：精密調査・性能計測・実装設計の確定

**目的**：単なる再調査で止めない。後続の正しい改善実装を可能にする、常用できる計測経路、独立した正確性の基準、採用可能な詳細設計を成果物として実装・PR提出する。

### 作業

1. 現mainの実行入口から、作品一覧→編集→保存→履歴→検索→関係図／年表→完全保存／復元→同期／限定共有まで、UI・domain・storage・Worker・DBテーブル・入出力・権限と依存を追跡。既存Drive「AUD-001～023」、2026-10-16監査「OPT-01～15」、既存104要件および116/464条項と相互参照する。
2. `src/App.tsx`, `src/storage/store.ts`, `src/domain/catalog.ts`, `src/domain/referenceChoices.ts`, `src/domain/contentValidationMemo.ts`, `src/ui/WindowedList.tsx`, `src/ui/fieldSpecs.ts`, `src/domain/types.ts`, `src/domain/linkCandidates.ts`, `.github/workflows/ci.yml`, `scripts/ci/ci_controls.py`等を出発点に、呼出元・重複・読込範囲を確認する。これらのpathだけに調査を限定しない。
3. 標準／大規模の既存試験入力を固定。追加検証用に作品1・10・50件、履歴100・1000・10000件、改名1件、台詞1件、密参照、固定世界、秘密データ、破損入力を作成し、既存fixtureとは別に管理する。
4. 処理区間別に、UI操作開始～編集可能／保存通知、DB読込行数・bytes、復号・複製、hash bytes、検証回数、索引生成回数、Worker転送量、実書込行数、メモリ保持と破棄を計測できる仕組みを追加する。測定機能は既定で無効／個人データをログしないものとし、測定のために製品の保存契約を変えない。
5. 原Standard/Large 30回の生値・180保存の区間を参照し、必要部分を同条件で再測定。旧Largeの起動p95 5731.5ms、検索p95 562.8ms、保存p95 5224.1ms、年表100ms／関係図50msは元の測定として扱い、実行環境と対象buildを付ける。測定できない場合は理由を明示する。
6. 改善候補ごとに最低2案＋現行方式を比較し、正確性、負の入力、保持量、読込数、速度、費用、移行、保守、戻し方を評価する。現行の正確な全件処理を対照として残し、候補の正しさは独立した期待データでも検査する。根拠のない全面改修は行わない。
7. 実行できる計測・回帰試験を実装し、設計判断と原因／反例／優先順位を保存する。明確な問題を発見しても第2段階の広域改修と混ぜず、別範囲とする。

### 成果物・完了条件

- `docs/optimization/phase1/` 等に、HEAD・対象build、104要件と監査候補の対応表、読込・更新依存図、原期待値、基準測定の生ログ、変更の影響表、採用／保留／棄却理由、変更前後の比較計画を保存。
- 計測用の非破壊コードと自動検査、追加fixture/manifestを新規Draft PRへ提出。既存の要件・原検査結果を改ざんしない。
- 少なくとも「何を減らせるか」「何を省くと正確性が壊れるか」「どの処理を誰が変更するか」が全主要候補で説明できる。実測できない箇所にはUNKNOWNを付ける。
- 第2段階へ渡す細分化された作業単位、依存関係、個別PRの検査、戻し方を確定する。

## 第2段階：根本的な性能・共通処理最適化の実装

**目的**：第1段階の証拠と、ユーザーが承認した設計方針を基に、必要な情報を必要時に必要量だけ取得／更新／検証する。局所改善だけを重ねるのではなく、正本と派生情報の境界を整理する。未承認の形式変更・機能採用は実装しない。

### 作業順序

1. **読込・起動・保持（OPT-01/02/05/07）**：作品一覧用の軽量なヘッダ取得と選択後の完全な編集準備を分離する。選択中の章・人物・関係・固定世界の必要な依存範囲を測定に従って限定する。DBからの取得件数とUI描画件数を混同しない。未読と存在しないものを明確に区別し、未選択作品の破損や旧版が他作品の作業を巻き込まないようにする。account/role/版変更・cancel・同時保存時の古い読込を排除し、未保存入力を維持する。
2. **保存・履歴・復元（OPT-03/04/11/13）**：変更対象と依存範囲を一度だけ計算する方式を検討し、保存前の全走査・hash・複製の重複を削減する。対象操作IDとrequest hashの再送判定、前後の履歴・64件復元点、projects/entities/commands/outbox/assetsの原子確定、冷却読込、旧形式互換、容量不足・中断・再試行は保持。履歴一覧は軽量なメタ情報を限定取得し、本文差分／復元情報は選択時に読む。変更の都度「局所結果と独立した全件検証」の完全一致を取る。
3. **検索・索引・参照・定義（OPT-06/08/09/10）**：作品・対象版・世界参照・アカウント・公開範囲・schema規則に結び付く共有派生索引を必要時構築し、依存変更時だけ無効化／再生成する。改名、別名、削除、世界固定版、権限取消、秘密情報に対して結果・順序と漏洩なしを全件対照で確認。タグは作者の分類／確認済み正式参照／自動提案／公開用索引を混ぜない。型・項目の意味・参照種別・検証・検索対象・公開可否の重複定義を整理し、表示文言・画面配置は必要に応じ独立させる。
4. **検証とWorker／描画（OPT-11/12、測定で問題が確定した箇所）**：`contentValidationMemo`の安全条件を維持。レコード内・参照先・作品全体・履歴全体の制約を分け、局所再利用できる範囲だけ最適化し、疑わしければ全件検証へ戻す。Worker転送・再描画・オブジェクト保持を、測定で主要原因と判明した場合にのみ改善する。
5. 実装を読込系、保存・履歴系、索引・定義系等のレビュー可能なPRに分け、段階ごとに結果・影響範囲・戻し方を残す。第1段階の実装を反映したmainを起点とし、別担当の同一path競合を避ける。

### 完了条件

- 既存104要件／原受入／固定版／履歴／秘密／同期・復元を失わない。標準・大規模・異常系・3ブラウザーの既存テストと追加の反例テストを成功させる。
- 同一対象版・同一入力・同一測定定義によって、起動、1件編集保存、履歴ページ、連続検索等のDB読込件数、検査／hash回数、画面待ち、メモリの前後差を実証する。改善しない案、劣化する案は無理に採用しない。
- 元のp95制限を維持する。大規模保存、年表・関係図等の原上限が存在しない項目には別の「改善目標案」を示すが、元合否を書き換えない。
- 移行・索引破損・認証変更・キャッシュ失効・容量不足・cold復元を含む独立の再検証を行う。PR本文に全数値・比較法・未実行条件を残す。

## 第3段階：制作機能の仕上げ・自動品質保証・引渡し

**目的**：元の要件全体が実際の制作作業としてつながり、実機以外で再現できる正常・失敗・例外を検証できるところまで完成させる。

### 作業

1. 104要件・116ケース・464条項、24工程、6回帰群を最新mainの製品コード、画面到達経路、使用fixture、実結果、欠落・外部条件に再対応付ける。実装が既にあれば修正や証拠の追加だけに限定する。
2. 小説／脚本、ゲーム制作者、世界設定監修、素材・翻訳、ディレクター／レビュー、個人のオフライン制作を想定し、「作成→入力→関連付け→本文→試読／検索／検査→変更履歴→公開範囲確認→出力→復元」を自動ブラウザーから連続して実行する。到達できない画面、不必要な入力、戻り位置の消失、未保存入力の喪失、意味の不明なエラー等、元要件に対する欠陥を修正する。実機でないタッチ模擬とキーボード・日本語文字列の検査は補助結果に限定する。
3. データの正確性を壊す例外を独立に試す：参照先不在、同名異ID、改名・分割・統合、異なる世界版、作者の真実／証言／仮説、状態の矛盾、分岐の到達不可、秘密出力、権限変更、重複送信、偽ACK、別アカウント、途中取消、未知major、破損bytes、途中保存／容量不足、復元後の再編集。
4. PRの検査時間を無駄なく短くする。対象差分ごとの早期検査とビルド／依存準備の重複抑制を検討するが、製品PRでは既存の必須試験数・assert・fixture・実ブラウザー3種・負のケース・失敗証拠を削らない。変更に関係のない純MarkdownだけのPRと製品／JSON／検査入力変更を区別し、証拠版が混ざらないようにする。並列化する場合は検査独立性と生証拠の完全性を実証する。
5. 原仕様の正式なStandard/Large各指標×30、原6条件×30の180保存、長時間7200秒、88,003記録＋113履歴・送信待ち＋実72MiB素材の完全ファイル、600000msの完全ファイル出力上限、2000ms進捗・取消を、変更後の同じ最終製品候補で再実行する。new/clone/cold・実bytesの照合と異常系も含める。重い試験は同じ資源上で直列に実施する。
6. X01～X12については、既存機能との重複・利用者価値・実装範囲・追加の受入ケース・互換/移行・費用・リスクを比較する採用判断資料を作る。**未採用のX機能を本体へ追加しない。** 個別採用が確定した場合だけ別PRに分けて実装し、その結果を元104要件の受入件数に混ぜない。
7. 元 `scripts/check_release.py` と24工程の判定を変更せず、原受入を根拠付きで更新する。実機試験、専用認証／サービス／対象ゲームに必要な実環境・権限が不足する部分は未実行・環境待ちのまま残し、自動試験結果で偽装しない。独立レビューに必要な再現物を揃える。

### 完了条件

- 正式な「自動・非実機で実行可能な」元受入条項を独立の実結果で判定し、元件数／元条件を維持。失敗・未実行・外部待ちを明確に区分し、差分のある原要件は修正されている。
- Standard/Large/長時間/障害/完全復元の生値、製品commit・build、fixture SHA、実ログ、検査結果、再実行コマンド、実証環境を保存する。速度とメモリの最終比較表を提供する。
- 製品CIと3ブラウザーの必須検査が成功し、証拠の保存・照合に成功する。元の公開判定が実機・実権限等でBLOCKEDならその結果を正しく保持し、合格・公開済みとはしない。
- 最終Draft PRに改善済み・要実機・要実認証・要対象ゲーム・要採用判断・その他の未解決を分け、再現方法と次に必要な一操作を残す。merge／公開はユーザーのみ。

## 段階の進行とPRの扱い

第1段階のDraft PR→ユーザーのレビュー・merge→更新mainから第2段階の小分けPR→ユーザーのレビュー・merge→第3段階の最終検証PRの順に進める。次の段階の実装は前段階の未統合コードを取り込み済みと仮定しない。未解決の阻害があっても独立できる作業を続け、完了と未完了を明示する。
