## 最重要：全段階共通の実施条件

1. 着手時にmain、open PR、HEAD/tree、対象の固定資料・検査入力・成果物を再取得。保護設定が未設定だったmainについても状態を確認し、設定変更は提案に留める。過去の資料にある「#48未統合」等の歴史記述を現在の状態と混同しない。既存機能・修正を重複実装しない。
2. 既存の104要件（B01–B24、F01–F60、N01–N20）、116受入ケースと464条項、24工程、6回帰群、68補助確認、形式の互換契約、元fixture/seed/実bytes/時間上限/取消・復元条件を削除・緩和・改名しない。追加X01–X12は未採用候補として別管理し、承認済み要件に自動昇格させない。
3. 既存の差分履歴・64操作ごとの復元点・編集用の履歴省略読込・差分書込・検証証拠の限定再利用・分割保存等は既存実装として再利用する。測定なしに「未実装」「遅い原因」と断定しない。
4. 守るべき不可侵条件：作品内IDの一意性、作者の入力・正式参照・履歴・固定版の不変性、真実／証言／仮説の違い、変更の一括確定、送信待ち・競合・拒否、旧形式の互換性、秘密／公開範囲／権限、完全ファイルからの全量復元、失敗時の元データ保全。速くなってもこれらが崩れた案は不採用。
5. 今回は実iPhone/iPad/PCによる実機試験は行わない。ブラウザ自動試験・ヘッドレス・自動のタッチ模擬は可能だが、実機合格と表現しない。22件の外部条件待ちは個別に実機依存と実認証・実サービス依存を分類し、後者は独立した許可済み試験環境・権限があれば検証、なければ保留。試験の代用で合格にしない。
6. 既存の別用途Supabase、本番DB、実ユーザー作品、認証・権限、支払、課金、公開・配備を変更しない。Codex Cloud environmentsを使用しない。秘密情報をPR・ログ・添付へ含めない。
7. 製品コードは新規ブランチから、影響範囲ごとにレビュー可能なDraft PRを作り、原因、変更ファイル、確認した原要件、前後の元測定値と生ログ、失敗・未実行、戻し方を記す。ユーザー以外はmergeせず、公開しない。CI失敗は原因を確認し、修正・再実行して最終状態を示す。承認待ちの間は別の独立作業を進められるが、同一pathを競合編集しない。
8. 速度・資源・正確性は別々に比較する。元数値は一切緩めず、原30回・180保存・600000ms・2000ms・7200秒の条件を変更しない。通常のPR検査は必要な影響範囲を先行し、各製品PRで必須全件・3ブラウザーの検査を通す。7200秒のような重い正式試験は統合された最終候補を同一条件で実施し、証拠の出所を固定する。


## 第2段階：根本的な性能・共通処理最適化の実装

**目的**：第1段階の証拠と、ユーザーが承認した設計方針を基に、必要な情報を必要時に必要量だけ取得／更新／検証する。局所改善だけを重ねるのではなく、正本と派生情報の境界を整理する。未承認の形式変更・機能採用は実装しない。

### 作業順序

1. **読込・起動・保持（OPT-01/02/05/07）**：作品一覧用の軽量なヘッダ取得と選択後の完全な編集準備を分離する。選択中の章・人物・関係・固定世界の必要な依存範囲を測定に従って限定する。DBからの取得件数とUI描画件数を混同しない。未読と存在しないものを明確に区別し、未選択作品の破損や旧版が他作品の作業を巻き込まないようにする。account/role/版変更・cancel・同時保存時の古い読込を排除し、未保存入力を維持する。
2. **保存・履歴・復元（OPT-03/04/11/13）**：変更対象と依存範囲を一度だけ計算する方式を検討し、保存前の全走査・hash・複製の重複を削減する。対象操作IDとrequest hashの再送判定、前後の履歴・64件復元点、projects/entities/commands/outbox/assetsの原子確定、冷却読込、旧形式互換、容量不足・中断・再試行は保持。履歴一覧は軽量なメタ情報を限定取得し、本文差分／復元情報は選択時に読む。変更の都度「局所結果と独立した全件検証」の完全一致を取る。
3. **検索・索引・参照・定義（OPT-06/08/09/10）**：作品・対象版・世界参照・アカウント・公開範囲・schema規則に結び付く共有派生索引を必要時構築し、依存変更時だけ無効化／再生成する。改名、別名、削除、世界固定版、権限取消、秘密情報に対して結果・順序と漏洩なしを全件対照で確認。タグは作者の分類／確認済み正式参照／自動提案／公開用索引を混ぜない。型・項目の意味・参照種別・検証・検索対象・公開可否の重複定義を整理し、表示文言・画面配置は必要に応じ独立させる。
4. **検証とWorker／描画（OPT-11/12、測定で問題が確定した箇所）**：`contentValidationMemo`の安全条件を維持。レコード内・参照先・作品全体・履歴全体の制約を分け、局所再利用できる範囲だけ最適化し、疑わしければ全件検証へ戻す。Worker転送・再描画・オブジェクト保持を、測定で主要原因と判明した場合にのみ改善する。
5. 実装を読込系、保存・履歴系、索引・定義系等のレビュー可能なPRに分け、段階ごとに結果・影響範囲・戻し方を残す。第1段階の実装を反映したmainを起点とし、別担当の同一path競合を避ける。

### 完了条件

- 既存104要件／原受入／固定版／履歴／秘密／同期・復元を失わない。標準・大規模・異常系・3ブラウザーの既存テストと追加の反例テストを成功させる。
- 同一対象版・同一入力・同一測定定義によって、起動、1件編集保存、履歴ページ、連続検索等のDB読込件数、検査／hash回数、画面待ち、メモリの前後差を実証する。改善しない案、劣化する案は無理に採用しない。
- 元のp95制限を維持する。大規模保存、年表・関係図等の原上限が存在しない項目には別の「改善目標案」を示すが、元合否を書き換えない。
- 移行・索引破損・認証変更・キャッシュ失効・容量不足・cold復元を含む独立の再検証を行う。PR本文に全数値・比較法・未実行条件を残す。
